1. Start here: the accurate project story

“I follow investment newsletters and otherwise have to search emails and chat announcements manually. My project extracts reported position changes, keeps their history, and lets me query them privately in Discord. It also manages my manually imported personal portfolio and delivers newsletter and Telegram news.”

Level 3 design: reusable workflows, persistent state, validation, branching, duplicate detection, bounded recovery and review. Scope: reported creator holdings, personal transaction records and private news. No brokerage trading, live-price synchronization or independently verified creator holdings. The personal sell calculation is a later extension; creator portfolio returns are not calculated.

Current state matters. A–I are active; J is a manual demonstration. A, B, D, E, F, G and H have draft versions different from their published versions. C and I match their published versions. Cleanup was saved to drafts; the published graphs were not changed by cleanup. Old execution pages retain their original graph. Do not publish simply to make a presentation screenshot match.

“Evaluations” here means selected saved executions. These links lead to real execution records, not an n8n Evaluations test dataset. All ten selected execution statuses were rechecked as successful for this document. Success does not mean every branch executed or every business action was performed.

4. Overall architecture, with data on each arrow

These are functional diagrams: a box may group several n8n nodes. Solid arrows show the labelled information passed. Green boxes are processing stages, blue boxes are decisions, gold boxes are durable storage, and grey boxes are external services. Read/write and orchestration paths are separated to keep the diagrams readable.

Additional core calls: /analyze in D passes one selected Gmail message to A. A calls B with normalized text; C revalidates evidence/state before writing. A records intake and notifications in Processing Log and sends its own private alerts. B calls the configured Gemini model and returns structured data; it never writes holdings itself.

F returns its prepared payload to I; I performs the Discord send. G/H fetch public Telegram previews on a schedule: this is polling, not an authenticated Telegram user session or an instantaneous push feed. They preserve the available post text and do not use AI or update positions.

5. Each workflow: purpose, start method, diagram and nodes to show

A — Email Processor

Starts: Gmail polling; also Execute Workflow for intake/recovery; separate manual tests.

Does: Coordinates creator email processing. It checks source and duplicate identity, freezes analysis, routes review/no-trade outcomes and calls C only for eligible events.

Produces: Normalized email → structured evidence → accepted update or review/no-op. A also records notification outcomes.

Exact nodes to locate: Dick Capital Gmail - every 5 minutes → Read original Dick Gmail message → Prepare live intake checkpoint → Call B - live review extraction → Frozen analysis route → Apply real positions through C

B — AI Analyzer

Starts: Called by A using Execute Workflow; manual regression and controlled-preview branches also exist.

Does: Interprets newsletter language with Gemini, then checks its output with deterministic code. A single evidence-review pass may be requested; unresolved results remain review/invalid.

Produces: Structured JSON with candidate events, evidence, source/portfolio/ticker, classification and permission-to-write decision.

Exact nodes to locate: When Executed by Another Workflow → Privacy and input gate → Build official Gemini request → Gemini LLM Chain - structured extraction → Deterministic validation → One review pass needed → Validate reviewed extraction

C — Position Manager

Starts: Called by A/E or an authorized test harness; no autonomous Gmail/Discord trigger.

Does: Maintains creator position state. It checks ownership and current data, plans one safe write, reads back, and repeats until the operation is reconciled.

Produces: Accepted history and derived Current Positions, or a review/no-op result. Baseline holdings remain separate from trade events.

Exact nodes to locate: Validate manager request → Read C writer ownership → Require C writer ownership → Read four-tab snapshot → Reconcile and plan one write → Finished → Write one reconciled range RAW → Return verified outcome

D — Discord Handler

Starts: Discord HTTPS webhook; manual fixtures/audits are separate branches.

Does: The user interface and authorization boundary. It verifies signatures before accepting commands, handles PING, acknowledges quickly and dispatches to a private read/write path.

Produces: Ephemeral formatted replies. Personal updates are handled here; creator analysis goes through A/B/C.

Exact nodes to locate: Discord interactions - private demo → Verify live signature - deployment gate → Acknowledge interaction → Allow approved private reads → Route private command → Build personal transaction update → Run A for manual notification

E — Error & Recovery

Starts: Error Trigger from linked workflows; five-minute scheduled scan; subworkflow recovery and manual tests.

Does: Logs technical failures and selects bounded recoverable work. It resumes checkpoints rather than blindly replaying every action. Classification uncertainty is review work, not an endless technical retry.

Produces: Sanitized failure logs/alerts, one selected recovery action, no-due result, or retry-exhausted review.

Exact nodes to locate: Automatic failure event → Sanitized live failure context → Append sanitized live failure → Send private technical failure alert → Recovery schedule - every 5 minutes → Select one bounded live retry → Resume one live A checkpoint → Resume one durable delivery

F — Market Intelligence

Starts: Gmail newsletter trigger; separate worker called by I; manual briefing fixtures.

Does: Separates article/news summarization from trade extraction. Intake queues message IDs; the worker verifies the source, calls Gemini, validates grounded output and stores the brief.

Produces: Stored newsletter metadata/brief and a payload returned to I. Never changes creator or personal holdings.

Exact nodes to locate: Approved newsletter Gmail trigger → Queue newsletter message identifiers → Dispatch each newsletter message → Newsletter worker input → Authorize and deduplicate real news → Gemini 3.5 Flash-Lite - real news → Validate grounded brief and prepare rows → Return saved brief delivery payload

G — Watcher Guru Relay

Starts: Five-minute scheduled poll; manual real-source probe.

Does: Reads the public Watcher Guru Telegram preview, selects unseen posts and sends original visible text through I.

Produces: Private guru-news relay and a durable receipt; no AI and no holdings update.

Exact nodes to locate: Fetch Watcher Guru public feed → Parse real Telegram posts → Read Watcher Guru relay receipts → Select unseen real posts → Deliver through durable queue → Verify Watcher Guru relay

H — New Rules Macro Relay

Starts: Five-minute scheduled poll; manual real-source probe.

Does: Reads New Rules public Telegram posts and relays unseen texts to the private Macro channel, one at a time through I.

Produces: Macro posts or full-text attachments when needed, plus durable relay receipts. No AI/position changes.

Exact nodes to locate: Fetch New Rules public feed → Select unseen real posts → New post decision → Relay posts one at a time → Deliver through durable queue → Verify New Rules relay → Finish Macro poll

I — Durable Delivery

Starts: Execute Workflow from F/G/H/E/J; separate manual operator controls.

Does: Reusable durable delivery service. It resolves a stable job, claims ownership, checkpoints attempts, prepares/freeze newsletter output if required and sends or reconciles delivery.

Produces: Verified receipt, already-complete no-op, retry-due state or manual-review outcome; releases only owned locks.

Exact nodes to locate: Resolve stable delivery job → Save attempt checkpoint → Prepare newsletter through F → Find prior Discord delivery → Save pending Discord send → Send one Discord message → Send full text attachment → Reconcile prior delivery → Return verified delivery status

J — Recovery Demonstration

Starts: Manual Trigger only. Not published as an automatic workflow.

Does: A repeatable demonstration of I’s delivery recovery and duplicate protection using a fictional job. The first attempt simulates a temporary pre-send 503.

Produces: One fictional private bot-errors message after retry, a skipped duplicate replay, and final proof. No position or Gemini calls.

Exact nodes to locate: Manual - demonstrate retry and duplicate safety → Attempt one - simulated temporary failure → Verify durable retry checkpoint → Wait for retry due time → Attempt two - recover and deliver → Repeat completed job - duplicate check → Show final demonstration proof

10. The database gap and a suitable multi-user extension

Honest answer: Google Sheets works as the current persistent store and makes the records easy to inspect. However, the provided rubric explicitly says “a Google Sheet alone does not count.” The project therefore does not currently demonstrate that database criterion. Calling Sheets a database or adding a diagram cannot fix that gap.

Recommended resource: PostgreSQL. It is a relational database supported by n8n’s Postgres node. It can enforce unique record identities, foreign-key relationships and transaction boundaries, which fit the project’s holdings, event history, processing jobs and future per-user portfolios. A PostgreSQL container would also supply the additional service required by the Docker section. Backfill with validation, preserve identifiers, compare results, and switch the reader and writer together. Do not create an unused database only for a screenshot. 11. Questions, recovery explanation and a short presentation order

E, I and J in plain language

E is the recovery coordinator. It hears about technical failures and scans saved work to choose an eligible retry. I is the delivery worker. It records the job/attempt, sends or reconciles the message, and saves the result. J is the demonstration harness. It deliberately creates a fictional failure, calls I again after the due time, and checks that replaying the completed job does not send twice. J does not prove that E’s timer fired or that a bad real API credential was handled.

Example: I saves attempt one, then the test simulates a 503 before sending. The job remains retryable. J waits, calls I again with the same identity, and attempt two sends once. J then calls I a third time; I sees completion and skips it. In production, E can select due jobs. If a send may have succeeded but its response was lost, I looks for prior delivery before sending again. Uncertainty may require review; this is not a claim of exactly-once delivery.
